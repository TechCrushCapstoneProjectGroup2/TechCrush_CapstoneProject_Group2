# LedgerPoint — Phase 0 Design Worksheet
**Project:** Secure Cloud File Storage System
**Team:** TECHCRUSH Group 2
**Cloud Provider:** Microsoft Azure
**Status:** Design in progress
## 2.1 Access Mechanism Decision

### Business Requirement

LedgerPoint needs to share confidential financial documents with external auditors without requiring them to create Azure accounts or sign in. Access must be secure, restricted, and temporary.

### Mechanisms Considered

| Criteria | Public Blob Storage | Private Blob Storage with SAS |
|---|---|---|
| External login required | No | No |
| Anonymous access | Public URLs allow access | Valid SAS required |
| Time-limited access | No automatic per-link expiry | Configurable expiry |
| Permission control | Public read access | Specific permissions, such as read-only |
| Confidentiality | Unsuitable | Suitable with secure configuration |

### Selected Mechanism

**Private Azure Blob Storage with short-lived, read-only user delegation SAS URLs.**

### Justification

We selected this mechanism because LedgerPoint handles sensitive financial statements that should not be accessible to the general public.

The private container prevents unauthenticated requests without valid authorization. A SAS URL provides temporary access to a specific document without requiring the external auditor to sign in.

A short expiration period, read-only permission, and HTTPS-only access reduce unnecessary exposure.

The solution will use Microsoft Entra ID and Azure RBAC to control employee access. Temporary sharing and early revocation will be implemented and tested.

### Design Considerations

- Disable anonymous public Blob access.
- Use least-privilege employee permissions.
- Prefer user delegation SAS over account-key-signed SAS.
- Avoid placing SAS URLs in source control or audit logs.
- Test both expiry and early revocation.
- Evaluate separate original and temporary-share containers before final implementation.

**Decision status:** Proposed — pending implementation and security verification.

## 2.2 Expiry and Revocation Policy

### Expiry Policy
LedgerPoint will use short-lived, read-only user delegation SAS URLs. The default validity period will be 30 minutes, with a configurable shorter interval for security testing. All external sharing will require HTTPS.

### Early Revocation
The proposed design maintains separate private containers for original documents and temporary shared copies. Each new share creates an individually named temporary copy. When an authorized employee revokes that share, the application deletes its temporary copy while preserving the original document.

### Security Considerations
- Keep SAS URLs confidential and never write their full contents to audit logs.
- Record the employee issuing or revoking a share, the target file, timestamp, expiry, and operation result.
- Limit each SAS URL to read access on one temporary file.
- Test successful access, expiry, and early revocation.
- Recognize that previously downloaded files cannot be recalled.
- Clean up expired temporary copies.

**Decision status:** Proposed; pending implementation and testing.


## 2.3 Logging Plan

### Objective
LedgerPoint will record important file operations to support accountability, security investigations, troubleshooting, and auditing.

### Logging Mechanisms
1. Application audit logs generated by the Bash CLI.
2. Azure Blob Storage diagnostic logs sent to a restricted Azure Monitor / Log Analytics destination.

### Required Events
| Action | Information Logged | Storage Location | Authorized Readers |
|---|---|---|---|
| Upload | Employee, file, timestamp, result | Application and Azure logs | Admin / compliance reviewer |
| List | Employee, container, timestamp, result | Application and Azure logs | Admin / compliance reviewer |
| Download | Employee/request information, file, timestamp, result | Application and Azure logs | Admin / compliance reviewer |
| Share | Issuer, intended recipient, file, expiry, result | Application audit log | Admin / compliance reviewer |
| Revoke | Employee, share identifier, time, result | Application and Azure logs | Admin / compliance reviewer |
| Delete | Employee, file, timestamp, result | Application and Azure logs | Admin / compliance reviewer |
| Failed access | Request details, timestamp, failure status | Azure diagnostic logs | Admin / compliance reviewer |

### Security Controls
- Never record complete SAS tokens, passwords, or storage account keys.
- Use UTC timestamps for consistent auditing.
- Restrict access to audit records using least-privilege permissions.
- Protect central logs against unauthorized changes or deletion.
- Record both successful and failed operations.
- Use synthetic test data during development.
- Document log retention and monitor logging costs.
- Recognize that SAS usage logs do not necessarily identify the human recipient.

**Decision status:** Proposed; pending implementation and verification.
